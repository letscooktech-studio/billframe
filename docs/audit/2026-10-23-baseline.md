## 1. Executive Summary & Root Cause Analysis

### The Critical Defect
Users reported that upon leaving and reopening the app (or navigating away to external apps such as UPI payment apps or sharing dialogs, and returning), all internal storage resets to a blank or default state, requiring the user to re-run the 5-step onboarding flow.

### Root Cause Isolation
Forensic examination of `src/data/database/DatabaseManager.ts` (lines 29–56) uncovered the direct source of this defect:
1. **Web Environment Misdetection in React Native**:
   ```typescript
   // src/data/database/DatabaseManager.ts
   const isWeb = typeof window !== 'undefined';
   ```
   In React Native (Android and iOS under Hermes or JavaScriptCore), `window` is polyfilled to point to the global execution context (`global.window = global;`). Consequently, `typeof window !== 'undefined'` evaluates to **`true`** on Android!
2. **Bypassing Native SQLite Storage**:
   Because `isWeb` is evaluated as `true` on Android, the code branch never calls `SQLite.openDatabaseAsync('billframe.db')`. Instead, it allocates an instance of `InMemorySQLiteDatabase`.
3. **Absence of Persistent Storage in the Memory Fallback**:
   Inside the web fallback, persistence relies on `window.localStorage`. On Android React Native, `window.localStorage` is `undefined`. Thus, all data is retained solely in volatile JavaScript memory (heap RAM).
4. **Process Lifecycle Loss**:
   When the user exits the app, switches to an external application (e.g., UPI apps like Google Pay, PhonePe, Paytm, or messaging apps), or when Android reclaims the activity under standard memory management, the React Native process is terminated. Upon cold relaunch, the heap is re-initialized from scratch.
5. **Cascading Onboarding Gate Trigger**:
   In `src/app/_layout.tsx`, `WorkspaceRepository.isOnboardingCompletedAsync()` queries the `workspace_preferences` table. Because the database was recreated in RAM, the table is empty, returning `onboardingCompleted: false`. This forces `_layout.tsx` to render `<OnboardingScreen />`, giving the user the impression that their entire business data has been wiped.

## 3. Storage Architecture & Persistence Lifecycle

### SQLite Database File
- **Target File**: `billframe.db`
- **Location**: Native application document directory managed by `expo-sqlite`.
- **Concurrency & Integrity Settings**:
  - `PRAGMA journal_mode = WAL;` (Write-Ahead Logging for atomic writes and zero concurrency locks)
  - `PRAGMA foreign_keys = ON;` (Strict referential integrity)

### Migration Engine (`MigrationRunner.ts`)
- **Version Tracking**: `migration_history` table stores `(version, name, checksum, applied_at)`.
- **Integrity Validation**: SHA-256 checksums verify that historical migrations have not been altered or corrupted.
- **Migration Registry (`registry.ts`)**: 12 sequential migrations from `v1_baseline_tables` through `v12_custom_document_instances`.

## 4. Remediation Plan

1. **Fix Platform Guard in `DatabaseManager.ts`**:
   Replace `typeof window !== 'undefined'` with `Platform.OS === 'web'`. Ensure Android strictly opens native `SQLite.openDatabaseAsync('billframe.db')`.
2. **Resilient Hydration Gate in `src/app/_layout.tsx`**:
   Ensure SQLite database initialization, migration completion, and security checks resolve before deciding whether to route to Onboarding or Dashboard.
3. **Persistence Regression Test Suite**:
   Create deterministic Jest integration tests simulating database restarts, closing and reopening `DatabaseManager`, and verifying that profile, sequence numbers, documents, and onboarding preferences remain intact.
4. **Fail-Safe Offline Backup/Restore (Gate 1)**:
   Verify `.bfbk` export and import routines with SHA-256 checksum validation and atomic transaction rollback.

## 5. Verification Results & Regression Evidence

### Execution of Fix
- In `DatabaseManager.ts`:
  - Added `import { Platform } from 'react-native';`
  - Replaced `const isWeb = typeof window !== 'undefined';` with `const isWeb = Platform.OS === 'web';`
  - On mobile platforms, exceptions during SQLite database initialization are no longer silently swallowed into a volatile memory store. An explicit error is thrown, protecting user data from silent loss.
  - Reset `this.webFallback = null` inside `closeDatabaseAsync()` for clean testing and restore resets.
- In `WorkspaceRepository.ts`:
  - Replaced fallback identifier `'default-profile'` with canonical `'default_business_profile'` matching `DatabaseManager.ts` and `BusinessProfileRepository.ts`.
